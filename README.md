# GoldenHour

**Severity Ranking and Hospital Readiness Matching System for Emergency Ambulance Response**

BCA 5th Semester mini project - KLE Technological University, Hubballi.
Theme 3: Search and Ranking System.

> **Academic simulation.** GoldenHour is not connected to 108 or any live emergency
> service. The default database is empty: organisations and patients register themselves,
> and hospitals enter their own data.

---

## Latest build: self-service onboarding + patient portal

The system no longer ships with demo hospitals, patients, stock or accounts. Every value
comes from the people who own it:

- A hospital registers its organisation and first staff login at `/register`.
- The hospital imports its complete dataset (CSV upload or JSON paste) covering licensed
  beds, free beds, blood units and medicines, then updates or adds individual values.
- A dispatcher registers an account, then registers the ambulance fleet.
- A patient registers with name, age and contact. The portal lets them call an ambulance,
  compare hospitals, pre-book a bed and read blood/organ donation campaign alerts.
- Hospitals confirm or decline pre-bookings and publish donation campaigns from their
  console. No sample patients, bookings or campaigns exist.

The original eight Gate 2 tables are unchanged in name and purpose. The patient portal
required new persistence, so this build adds the `PATIENT` role, a nullable
`users.patient_id` link, and three portal tables: `prebooking`, `campaign` and
`campaign_read`. The role/link CHECK now has a patient branch; no Gate 2 table was dropped
or renamed. Onboarding and imports still write only `hospital`, `users`, `blood_stock`
and `medicine_stock`.

## Getting started (empty system)

```bash
npm install
cp .env.example .env      # set JWT_SECRET
npm run db:setup          # init cluster, migrate - no demo data
npm run dev               # API :4000 + web :3000
```

Then:

1. Open `http://localhost:3000/register`, choose **Hospital**, and enter the hospital name,
   map coordinates, licensed beds and the first staff username/password. You are signed in
   automatically and land on **Beds & resources**.
2. Open **Import dataset** in the hospital sidebar. Upload a CSV or paste JSON with beds,
   blood groups and medicines (template buttons are on the page). The import replaces the
   current dataset in one transaction.
3. After the first import, **Beds & resources** lets you change free beds, update any
   blood group or medicine, and add a new medicine or blood group individually.
4. Register a **Dispatcher** account from the same page, then open **Ambulance fleet** and
   add each vehicle (registration number, coordinates, status). Only AVAILABLE vehicles
   are searched.
5. Dispatchers register emergencies; queue, matching, assignment and closure work as
   before.
6. Open **Patient portal** on the landing page, register a patient, then use **Call an
   ambulance**, **Hospitals** and **Notifications**. Your patient ID is generated by the
   server and is the only identity attached to calls and pre-bookings.
7. In the hospital console, use **Pre-bookings** to confirm or decline patient requests
   and **Donation campaigns** to publish blood or organ donation camps. Confirming a
   pre-booking reserves one free bed; cancelling returns it.

**Optional presentation data:** `npm run db:seed:demo` loads the old sample hospitals,
accounts, fleet and requests (documented below) for rehearsing the scripted demo. It is
never loaded by `db:setup`.

## Registration and onboarding

```
POST /api/auth/register/hospital     (public)
POST /api/auth/register/dispatcher   (public)
POST /api/auth/register/patient      (public)
```

- Passwords are hashed with bcrypt; usernames are unique and validated (3-60 chars).
- A hospital registration creates the hospital and its first HOSPITAL user in one
  transaction, signs the user in, and starts with **0 free beds and no stock**. The
  hospital ID is generated by the server (`HOSP-XXXXXX`), never chosen by the client.
- A dispatcher registration creates a DISPATCHER user with no hospital link.
- A patient registration creates a `patient` row (name, age, 10-digit contact) and its
  PATIENT login in one transaction. The patient ID (`PAT-XXXXXXXX`) is generated by the
  server; identity on every portal call comes from the session, never the request body.
- The database CHECK constraint enforces the role/link relationship: PATIENT users need a
  `patient_id` and no `hospital_id`, and staff roles need the reverse.

## Hospital dataset import

```
POST /api/hospital/resources/import   (hospital staff, own hospital)
```

JSON body (the CSV template maps to the same structure):

```json
{
  "totalBeds": 120,
  "freeBeds": 8,
  "bloodStock": [{ "group": "O+", "units": 6 }],
  "medicineStock": [{ "medicine": "Adrenaline", "units": 25 }]
}
```

- The dataset is **authoritative**: blood groups and medicines not present are removed.
  One locked transaction updates beds and replaces both stock lists, so a failed row
  changes nothing.
- Validation: 1-20,000 total beds, free beds within the total, units 0-9999, the eight
  standard blood groups, unique groups/medicines, medicine names 3-80 characters, at most
  8 blood groups and 50 medicines.
- CSV format is `type,name,value`:
  `beds,total`, `beds,free`, `blood,O+`, `medicine,Adrenaline`. The page parses the file
  locally and sends the same JSON; the template is downloadable from the import page.

### Individual updates

```
PATCH /api/hospital/resources        (hospital staff, own hospital)
```

Accepts any combination of `freeBeds`, `bloodStock`, `medicineStock`. A medicine name
that is not tracked yet is **created**; an existing name is updated case-insensitively. A
blood group is upserted. Free beds are checked against the hospital's licensed total.

### Individual removal

```
DELETE /api/hospital/resources/blood/:group         (hospital staff, own hospital)
DELETE /api/hospital/resources/medicine/:medicine   (hospital staff, own hospital)
```

Stops tracking one blood group or medicine without re-importing the dataset. The delete
runs in a transaction that locks the hospital row, is scoped to the session's hospital,
and returns 404 when the row is not tracked; medicine names match case-insensitively.
Readiness matching treats a removed row as not in stock on the next match.

## Fleet

```
GET  /api/ambulances      (dispatcher)
POST /api/ambulances      (dispatcher)
```

The fleet starts empty. Registration numbers must match the Gate 2 format
(`KA-25-AB-4821`), coordinates must be valid, and the status may be AVAILABLE, BUSY or
OFFLINE (default AVAILABLE). The search endpoint only ever fetches AVAILABLE vehicles.

## Patient portal

```
GET  /api/patient/overview              (patient)
GET  /api/patient/hospitals             (patient)
GET  /api/patient/requests              (patient)
POST /api/patient/requests              (patient)
GET  /api/patient/prebookings           (patient)
POST /api/patient/prebookings           (patient)
PATCH /api/patient/prebookings/:id/cancel (patient)
GET  /api/patient/campaigns             (patient)
POST /api/patient/campaigns/:id/read    (patient)
POST /api/patient/campaigns/read-all    (patient)
```

- **Call an ambulance** creates a normal QUEUED `emergency_request` with the patient's
  own `patient_id` and user as `raised_by`. Dispatchers see it in the same priority queue
  as any other call; severity ranking, ambulance search and hospital matching are
  unchanged.
- **Check hospitals** lists every hospital with its live free beds, blood groups and
  medicine count. A patient can only pre-book an accepting hospital (free beds > 0).
- **Pre-booking** reserves a one-hour, on-the-hour slot. It starts PENDING and does not
  consume a bed. Hospital staff confirm or decline. Confirming locks the hospital row,
  requires a free bed and decrements it; declining changes nothing.
- **Cancellation requests:** cancelling a PENDING booking is immediate (no bed was
  reserved). Cancelling a CONFIRMED booking becomes a request - the bed stays reserved
  until hospital staff approve it (bed returned, clamped at capacity) or reject it (the
  booking returns to CONFIRMED). The patient's reason is stored and shown to the hospital.
- **Admission and discharge:** staff admit a confirmed patient (the reserved bed becomes
  occupied) and discharge them later, which releases the bed back to the hospital.
- Every transition is validated against the current status, runs in one transaction that
  locks the pre-booking row, and patients only ever see and act on their own bookings.
- **Notifications** are hospital-published campaigns of type `BLOOD_DONATION` or
  `ORGAN_DONATION`. Patient read receipts live in `campaign_read`, so unread counts and
  the `Mark all read` action are per patient. No email or SMS is sent.

Hospital staff endpoints:

```
GET   /api/hospital/prebookings          (hospital, own hospital)
PATCH /api/hospital/prebookings/:id      (hospital action, see below)
GET   /api/hospital/campaigns            (hospital, own hospital)
POST  /api/hospital/campaigns            (hospital)
```

`PATCH /api/hospital/prebookings/:id` takes `{ "action": "..." }` with one of
`CONFIRM`, `DECLINE`, `ADMIT`, `DISCHARGE`, `APPROVE_CANCELLATION` or
`REJECT_CANCELLATION` (`{ "status": "CONFIRMED" | "DECLINED" }` is still accepted).
Allowed transitions:

| From | Action | To | Bed effect |
| --- | --- | --- | --- |
| PENDING | CONFIRM | CONFIRMED | reserves one free bed |
| PENDING | DECLINE | DECLINED | none |
| PENDING | patient cancel | CANCELLED | none |
| CONFIRMED | ADMIT | ADMITTED | none (bed already reserved) |
| CONFIRMED | patient cancel | CANCEL_REQUESTED | none until approved |
| CANCEL_REQUESTED | APPROVE_CANCELLATION | CANCELLED | releases the bed |
| CANCEL_REQUESTED | REJECT_CANCELLATION | CONFIRMED | keeps the bed |
| ADMITTED | DISCHARGE | DISCHARGED | releases the bed |

Any other transition returns 409 `INVALID_TRANSITION`.

## Severity ranking

```
priorityScore = severityWeight × 1000 + min(waitingMinutes, 999)
CRITICAL 4   HIGH 3   MEDIUM 2   LOW 1
```

Severity can never be overtaken by waiting; inside a severity the longest wait is first;
ties use the older `created_at`, then the request ID. Only QUEUED calls are ranked;
assigned calls are listed separately.

## Ambulance search

`GET /api/ambulances/search?requestId=` (or `?lat=&lon=`) computes Haversine distance to
every AVAILABLE ambulance, nearest first, with
`ETA = max(3, round(km / 35 × 60))` minutes at a documented 35 km/h average.

## Hospital readiness

Eligibility is at least one free bed. Score = blood 40 + medicine 40 + nearness 20.
Blood/medicine award full points when in stock or not required; nearness is
`20 × max(0, 1 − d/25)` on Haversine kilometres. Missing requirements set `partialFlag`.

## Assignment and closure

`POST /api/assignments` locks the request, ambulance and hospital rows in one transaction,
recomputes readiness, writes the assignment, sets the ambulance BUSY, marks the request
ASSIGNED and decrements free beds. `POST /api/assignments/:id/close` reverses it: closes
the assignment, marks the request CLOSED, returns a BUSY ambulance to AVAILABLE and
restores the bed (clamped at total capacity).

## Live updates

Socket.IO at `/socket.io` verifies the session cookie during the handshake and broadcasts
only an entity/action signal after a write. Clients refetch through their role-guarded
REST endpoints; a 20-second poll remains as fallback. Events cover emergency creation,
assignment, closure and hospital updates.

## Security

bcrypt hashes, 8-hour HS256 JWT in an HttpOnly SameSite cookie, role guards that re-read
the user from PostgreSQL, login throttling after five failures, server-side validation on
every write, hospital scoping from the session (never a URL parameter), and Gate 2 CHECK
constraints as the final backstop.

## Known limitations

1. The import replaces the dataset; there is no merge mode or import history.
2. Fleet vehicles can be registered only with an initial status; there is no edit screen.
3. Free beds are declared by staff, not derived from admissions or discharges.
4. Closing a case records no clinical outcome and cannot be reopened.
5. Blood and medicine readiness is binary "at least one unit"; quantities only drive the
   low-stock display.
6. Straight-line distance and a fixed 35 km/h ETA; no routing or traffic.
7. Live updates use the in-memory Socket.IO adapter (single API process).
8. Public registration is open by design for this academic project; production deployment
   would add approval and email verification.
9. A pre-booking reserves one bed for a one-hour slot but is not tied to a specific
   physical bed; there is no automatic expiry or no-show handling if the patient never
   arrives.
10. Campaign notifications are in-app only - there is no email, SMS or push delivery, and
    campaigns are not editable after publishing.
11. Patient-raised calls cannot be cancelled by the patient; a dispatcher closes the case.
12. The bundled PostgreSQL is a development convenience.
